# Constitución del backend

## 1. Objetivo

Definir la base tecnológica, arquitectónica y las fases de construcción del backend para el sistema de gestión del gimnasio.

El backend expondrá una API REST para administrar la autenticación del administrador y la gestión de clientes almacenados en PostgreSQL.

## 2. Tecnologías seleccionadas

| Área | Tecnología | Propósito |
|---|---|---|
| Lenguaje | TypeScript | Tipado estático y mantenibilidad del código. |
| Runtime | Node.js 20 o superior | Ejecución del backend y compatibilidad con Vercel. |
| Capa HTTP | Hono.js | Construcción de la API REST, rutas y middleware. |
| Despliegue | Vercel Functions | Despliegue serverless del backend. |
| Base de datos | PostgreSQL | Persistencia de administradores y clientes. |
| Acceso a datos | `pg` | Conexión y consultas parametrizadas hacia PostgreSQL. |
| Autenticación | JWT | Identificación y autorización del administrador. |
| Hash de contraseñas | `bcrypt` | Almacenamiento seguro de contraseñas con 8 saltos. |
| Validación | Zod | Validación de cuerpos, parámetros, filtros y variables de entorno. |
| Pruebas | Vitest | Pruebas unitarias e integración. |
| Calidad | ESLint y Prettier | Reglas de calidad y formato uniforme. |

## 3. Arquitectura propuesta

Se utilizará una arquitectura de **tres capas**, adecuada para una API REST y más clara para este proyecto que un MVC tradicional completo.

```text
backend/
├── src/
│   ├── app.ts
│   ├── server.ts
│   ├── config/
│   │   └── env.ts
│   ├── routes/
│   │   ├── auth.routes.ts
│   │   └── clientes.routes.ts
│   ├── controllers/
│   │   ├── auth.controller.ts
│   │   └── clientes.controller.ts
│   ├── services/
│   │   ├── auth.service.ts
│   │   └── clientes.service.ts
│   ├── repositories/
│   │   ├── administrador.repository.ts
│   │   └── cliente.repository.ts
│   ├── schemas/
│   │   ├── auth.schema.ts
│   │   └── cliente.schema.ts
│   ├── middlewares/
│   │   ├── auth.middleware.ts
│   │   └── error.middleware.ts
│   ├── db/
│   │   └── pool.ts
│   └── types/
│       └── auth.types.ts
└── tests/
```

### Responsabilidades de cada capa

#### Rutas y controladores

- Definir los endpoints HTTP.
- Recibir las solicitudes.
- Validar la entrada con esquemas Zod.
- Invocar los servicios correspondientes.
- Devolver respuestas y códigos HTTP.

#### Servicios

- Contener la lógica de negocio.
- Gestionar el inicio y cierre de sesión.
- Comparar contraseñas con `bcrypt`.
- Generar y validar la información de los JWT.
- Coordinar las operaciones de clientes.

#### Repositorios

- Ejecutar consultas contra PostgreSQL.
- Utilizar consultas parametrizadas.
- Encapsular el acceso a las tablas `Administrador` y `Cliente`.
- Evitar que los controladores y servicios dependan directamente de SQL.

## 4. Funcionalidades requeridas

### 4.1 Inicio de sesión del administrador

```http
POST /api/auth/login
```

- Recibir `nombreUsuario` y `contrasena`.
- Buscar al administrador.
- Comparar la contraseña mediante `bcrypt`.
- Generar un JWT si las credenciales son válidas.
- No devolver la contraseña en ninguna respuesta.

### 4.2 Cerrar sesión del administrador

```http
POST /api/auth/logout
```

El JWT es stateless. Para el MVP, el endpoint responderá correctamente y el cliente deberá eliminar el token almacenado.

Para invalidar tokens inmediatamente en el servidor será necesario implementar posteriormente una estrategia de revocación, por ejemplo, una tabla de sesiones o tokens revocados.

### 4.3 Registrar clientes

```http
POST /api/clientes
Authorization: Bearer <token>
```

Solo un administrador autenticado podrá registrar clientes. Los datos serán validados con Zod y las reglas de PostgreSQL.

### 4.4 Actualizar clientes

```http
PUT /api/clientes/:id
Authorization: Bearer <token>
```

Solo un administrador autenticado podrá modificar la información de un cliente existente.

### 4.5 Listar clientes

```http
GET /api/clientes
Authorization: Bearer <token>
```

La respuesta deberá devolver los clientes sin exponer información sensible del administrador.

### 4.6 Listar clientes filtrados

```http
GET /api/clientes?nombreCliente=Juan&tipoEntrada=mensual&tipoPago=QR
Authorization: Bearer <token>
```

Se podrán soportar filtros por:

- `nombreCliente`.
- `telefono`.
- `tipoEntrada`.
- `tipoPago`.
- Rango de `fechaRegistro`.

Los filtros deberán utilizar consultas parametrizadas y validarse con Zod.

## 5. Rutas propuestas

| Método | Ruta | Autenticación | Descripción |
|---|---|---|---|
| `POST` | `/api/auth/login` | No | Iniciar sesión como administrador. |
| `POST` | `/api/auth/logout` | Sí | Cerrar la sesión del administrador. |
| `POST` | `/api/clientes` | Sí | Registrar un cliente. |
| `PUT` | `/api/clientes/:id` | Sí | Actualizar un cliente. |
| `GET` | `/api/clientes` | Sí | Listar clientes o aplicar filtros. |
| `GET` | `/health` | No | Comprobar disponibilidad de la API. |

## 6. Seguridad

- Las contraseñas nunca se almacenarán en texto plano.
- `bcrypt` se utilizará con ocho saltos:

  ```ts
  const hash = await bcrypt.hash(contrasena, 8)
  ```

- Los JWT utilizarán una clave secreta almacenada en variables de entorno.
- Se configurarán expiración, emisor y audiencia del JWT.
- Las rutas privadas exigirán el encabezado `Authorization: Bearer <token>`.
- Los datos de entrada se validarán con Zod.
- Las consultas a PostgreSQL serán parametrizadas.
- Los secretos no se incluirán en el repositorio.
- Las contraseñas no aparecerán en logs ni respuestas.
- Se añadirá middleware global para errores y respuestas consistentes.
- Se configurará CORS únicamente para los orígenes autorizados.

## 7. Variables de entorno

```env
NODE_ENV=development
PORT=3000
DATABASE_URL=postgresql://usuario:contrasena@host:5432/gimnasiodb
JWT_SECRET=clave-secreta-larga-y-segura
JWT_ISSUER=gimnasiodb-api
JWT_AUDIENCE=gimnasiodb-client
JWT_EXPIRES_IN=1h
```

Todas las variables de entorno deberán validarse al iniciar la aplicación mediante Zod.

## 8. Compatibilidad con Hono y Vercel

La documentación oficial de Hono indica que existe una plantilla para Vercel y que una aplicación Hono puede desplegarse con configuración mínima. La aplicación debe exportarse como una exportación por defecto:

```ts
import { Hono } from 'hono'

const app = new Hono()

export default app
```

El desarrollo local podrá ejecutarse con:

```bash
vercel dev
```

El despliegue podrá realizarse con:

```bash
vercel deploy
```

Vercel soporta TypeScript en sus funciones con runtime Node.js y proporciona compatibilidad con las APIs de Node.js. Hono también puede ejecutarse localmente con Node.js utilizando `@hono/node-server`.

### Consideraciones serverless

- El pool de PostgreSQL debe reutilizarse entre invocaciones cuando sea posible.
- No se debe abrir una conexión nueva de forma innecesaria por cada solicitud.
- No se debe depender del almacenamiento local de archivos para sesiones.
- Las variables de entorno se configurarán en Vercel Environment Variables.
- La aplicación Hono debe mantenerse compatible con el modelo de ejecución de Vercel.
- `bcrypt` debe probarse durante el proceso de build y despliegue por utilizar componentes nativos en algunas instalaciones.

## 9. Fases de construcción

### Fase 1: Inicialización

- Crear el proyecto TypeScript.
- Configurar `package.json` y el gestor de paquetes.
- Configurar `tsconfig.json`.
- Configurar ESLint, Prettier y Vitest.
- Crear la aplicación Hono.
- Preparar el punto de entrada compatible con Vercel.

### Fase 2: Configuración y base de datos

- Configurar las variables de entorno.
- Validar las variables con Zod.
- Crear el pool de PostgreSQL.
- Configurar la base de datos `gimnasiodb`.
- Verificar la conexión con PostgreSQL.
- Integrar los scripts SQL existentes.

### Fase 3: Repositorios

- Crear el repositorio de administradores.
- Implementar la búsqueda por `nombreUsuario`.
- Crear el repositorio de clientes.
- Implementar inserción de clientes.
- Implementar actualización de clientes.
- Implementar listado general.
- Implementar filtros dinámicos con consultas parametrizadas.

### Fase 4: Validación

- Crear esquemas Zod para el login.
- Crear esquemas para registrar y actualizar clientes.
- Crear esquemas para parámetros y filtros.
- Crear mensajes de error consistentes.
- Validar variables de entorno al iniciar.

### Fase 5: Autenticación y autorización

- Implementar comparación de contraseñas con `bcrypt`.
- Generar JWT después de un login válido.
- Configurar expiración, emisor y audiencia.
- Crear middleware de autenticación con `hono/jwt`.
- Proteger las rutas de clientes.
- Implementar el endpoint de logout.

### Fase 6: Casos de uso de clientes

- Implementar el registro de clientes.
- Implementar la actualización de clientes.
- Implementar el listado general.
- Implementar el listado filtrado.
- Manejar clientes inexistentes.
- Manejar duplicados y datos inválidos.

### Fase 7: Errores, observabilidad y seguridad

- Crear middleware global de errores.
- Definir formato estándar de respuestas.
- Configurar CORS.
- Añadir logs sin información sensible.
- Añadir ruta `/health`.
- Revisar códigos HTTP y manejo de excepciones.

### Fase 8: Pruebas

- Probar login correcto.
- Probar credenciales incorrectas.
- Probar JWT inválido y expirado.
- Probar registro de clientes.
- Probar actualización de clientes.
- Probar listado general.
- Probar filtros.
- Probar validaciones y códigos HTTP.
- Probar la conexión y las consultas contra PostgreSQL.

### Fase 9: Despliegue

- Configurar variables de entorno en Vercel.
- Configurar la base de datos PostgreSQL accesible desde Vercel.
- Ejecutar localmente con `vercel dev`.
- Ejecutar el build y las pruebas.
- Desplegar con Vercel.
- Probar los endpoints desplegados.
- Verificar logs y tiempos de respuesta.

## 10. Criterios de aceptación

- El administrador puede iniciar sesión con credenciales válidas.
- Las contraseñas se almacenan usando `bcrypt` con ocho saltos.
- Las rutas privadas rechazan solicitudes sin JWT válido.
- El administrador puede registrar y actualizar clientes.
- El administrador puede listar clientes.
- El administrador puede filtrar clientes.
- Los datos inválidos reciben respuestas `400`.
- Las credenciales inválidas reciben una respuesta `401`.
- Los recursos inexistentes reciben una respuesta `404`.
- Los errores internos no exponen información sensible.
- El backend puede ejecutarse localmente y desplegarse en Vercel.
